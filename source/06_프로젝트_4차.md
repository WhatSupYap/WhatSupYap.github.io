## 아키텍처

### 시스템 구조
```
사용자 → Nginx → Gunicorn → Django
    ├── Web (VIEW): HTML 렌더링
    └── Chatbot (REST API)
        ├── DB Handler → PostgreSQL
        ├── CHAT Handler → LangGraph
        └── LLM Handler → OpenAI API
```

### LangGraph 구조

#### 5가지 의도 분류
1. **search**: 공고 검색 (RDB + RAG)
2. **select**: 공고 선택
3. **detail**: 공고 상세 정보 (RAG)
4. **compare**: 다중 공고 비교
5. **chat**: 일반 대화 / 웹 검색

#### 상태 관리
- `prev_anncs`: 이전 검색 결과
- `selected_annc`: 선택된 공고
- `search_history`: 검색 이력

## 3차 → 4차 주요 개선사항

### 3차 프로젝트의 문제점
- **선형 파이프라인**: 4~5회 LLM 호출
- **맥락 유실**: 이전 대화 상태 미유지
- **비효율성**: 매번 전체 파이프라인 실행

### 4차 개선사항 (LangGraph)
- **상태 기반 그래프**: 의도 분류 후 분기
- **상태 유지**: 대화 컨텍스트 유지
- **효율성**: 1회 LLM 호출로 의도 분류

### 상태 기반 대화 예시
```
사용자: "전라도 행복주택 알려줘"
→ intent: search 
→ prev_anncs: [나주이창, 완주삼봉] 저장

사용자: "1번 선택"
→ intent: select (prev_anncs 참조)
→ selected_annc: 나주이창 저장

사용자: "신청자격 알려줘"
→ intent: detail (selected_annc 참조)
→ RAG 검색 수행

사용자: "1번이랑 2번 비교해줘"
→ intent: compare (prev_anncs 참조)
→ 비교 분석
```
